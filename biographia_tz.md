# Техническое задание — модуль «Biographia»

**Статус:** черновик для вычитки
**Назначение документа:** зафиксировать согласованную концепцию перед подготовкой промта для реализации в Claude Code.

---

## 1. Назначение и контекст

Biographia — модуль экосистемы SSOD/Dominex для ведения документации по объектам системы. Он позволяет привязывать к сущностям Dominex (серверам, оборудованию, юрлицам и т. п.) официальную «биографию» — хронологию событий с текстом и вложениями (фото, сканы, файлы, аудио/видео), а также вести личные записи и личный дневник владельца.

Ключевые задачи:

- Централизованная официальная вики по элементам инфраструктуры и юрлицам.
- Разделение информации по уровню закрытости (открытая / по юрлицу / личная) без смешения между организациями.
- Личный зашифрованный дневник, недоступный никому, кроме владельца.
- Ввод информации с разных устройств, включая оперативные заметки и фото «на лету» с телефона.

Biographia — не поле «заметка/комментарий». Комментарии — неформальный канал (админ↔админ, пометка пользователю). Biographia — официальная, авторская, версионируемая запись, часть канонической истории объекта.

## 2. Экосистема и интеграция

Существующие сервисы:

- **Dominex** (`dominex.ssod.pro`) — ядро identity/access. Flask 3.x, Flask-Login, Flask-SQLAlchemy (SQLAlchemy 2.x), Flask-Migrate/Alembic, PostgreSQL (psycopg2), PyJWT (SSO-тикеты), gunicorn, Docker Compose. Ведёт сущности, свойства, шаблоны, юрлица, ранговую модель доступа.
- **ssod_auth** (`auth.ssod.pro`) — шлюз аутентификации/сессий. Django 5.2, django-otp + django-otp-webauthn (passkeys), PostgreSQL, PyJWT, requests. Здесь же — ЛК пользователя и учёт ключей.
- **ssod_site** — публичный сайт (Django, общий образ с ssod_auth).

Общее: PostgreSQL, Docker Compose, gunicorn, nginx+certbot на одном хосте. Интеграция между сервисами — HTTP API с shared-secret заголовком `X-Dominex-Api-Key` + PyJWT для SSO-тикетов. Визуальная база — дизайн-система `atb-portal` (сайдбар, CSS custom properties, светлая/тёмная тема).

**Biographia** добавляется как отдельный сервис по тому же паттерну:

- Отдельный Flask-сервис (Docker Compose на том же хосте за nginx), интеграция с Dominex/ssod через `X-Dominex-Api-Key` + PyJWT.
- Ранги, юрлица и сущности берутся из Dominex по API (Biographia не владеет ими и не лезет в его таблицы напрямую).
- Авторизация — через единый ЛК (ssod). Вход в модуль доступен при наличии права на Biographia.

### 2.1. Веб-вход — реализовано и проверено 2026-07-13

Раздел 4.1 описывает только мобильную привязку. Отдельно нужен обычный веб-вход в SPA (Фаза 1) — он не то же самое и использует **уже готовый и проверенный в проде** механизм SSO-тикета, которым Dominex сам входит через `ssod_auth` (не изобретался заново):

- `ssod_auth`: `sso_enabled=True` включён на `Product`-строке `biographia` (через новый экран настроек Dominex, раздел 13 — не вручную в БД); кнопка в сайдбаре Dominex/ЛК будет вести на `GET /account/sso/authorize/biographia/`.
- Biographia: `GET /auth/sso/callback` (`app/auth/routes.py`) — статическая проверка JWT (подпись + `exp` + `aud=biographia`, без обратного похода к `ssod_auth`) и защита от повторного использования тикета через собственную таблицу `SsoTicketUse(jti)` (миграция `0001_sso_ticket_use`) — один в один по образцу `dominex/app/auth/routes.py::sso_callback`.
- **Отличие от Dominex, из-за которого код не 1:1 копия**: у Dominex есть локальная таблица `User`, у Biographia — нет (она не владеет идентичностью, TZ раздел 2/6.1). Поэтому после проверки тикета Biographia не ищет локального пользователя, а обращается к проекции Dominex (`GET /api/v1/identity/projection/users/<username>`, свой ключ из 2.2) и **дополнительно** проверяет там активный грант `biographia` — сознательный defense-in-depth поверх уже сделанной проверки в `ssod_auth`, а не дублирование ради дублирования: `ssod_auth`'s `UserProductAccess` — синхронизируемый кэш, реальный источник истины по грантам — `ProductAccessGrant` в Dominex, и это могут разъехаться. Личность на сессию кладётся в подписанную Flask-сессию (`username`/`display_name`/`access_class`/`organization`) — локального хранилища пользователей пока нет, вся идентичность живёт в сессии между запросами.
- Не путать с 4.1: тикет даёт браузерную сессию в Biographia; для расшифровки личной зоны в этой же сессии всё равно нужен отдельный доступ к мастер-ключу с этого устройства (тот же принцип, что и в мобильном потоке, просто без пейринг-ключа — устройство уже опознано по факту наличия браузерной сессии/passkey).

**Проверено сквозь реальный docker-стек** (не хендролленный тикет — настоящий, выпущенный `ssod_auth`'s `sso_authorize` через Django test client с реальным `force_login`): валидный тикет → сессия → `/whoami` отдаёт личность; повтор того же тикета → 401; чужая `aud`, просроченный, битый тикет → 401 на каждый; тикет валиден в `ssod_auth`, но в Dominex грант отозван → 403 (сработала именно вторая, defense-in-depth проверка, не первая) — временно отозвал грант admin→biographia в Dominex, убедился в 403, вернул обратно. UI (кнопка в сайдбаре Dominex, реальный браузерный переход) пока не подключён — Phase 1 SPA ещё не начата, весь путь проверен напрямую по HTTP.

### 2.2. `X-Dominex-Api-Key` — решено: у каждого сервиса свой ключ

Подтверждено: `ssod_auth` и Biographia (и любой следующий потребитель identity-API) получают **раздельные** секреты, не общий `INTEGRATION_API_KEY`. Причина — компрометация одного сервиса не должна давать доступ к identity-API от имени другого; тот же класс риска, что и прошлый инцидент с разъехавшимся `DOMINEX_API_KEY`/`DOMINEX_INTEGRATION_API_KEY` (см. память по SSOD-интеграции), только теперь предотвращённый архитектурно, а не через синхронизацию `.env`.

Механизм — зеркалирует уже существующий в Dominex паттерн для `app/api/import_sync.py` (`ExternalSource.api_key`, ключ хранится на строке конкретного источника, а не общей константой), применённый к identity-blueprint:

- Новая таблица консьюмеров identity-API (например `IdentityApiConsumer`: `code`, `name`, `api_key`, `is_active`) вместо одного значения `INTEGRATION_API_KEY` в конфиге.
- `require_integration_key()` в `app/api/identity.py` ищет консьюмера по присланному ключу вместо сравнения с одной константой.
- Миграция данных: существующий `INTEGRATION_API_KEY` (сейчас используется `ssod_auth`) переносится в первую строку этой таблицы как есть — `ssod_auth`'s `.env` менять не нужно, ключ тот же, меняется только то, где Dominex его хранит и с чем сравнивает.
- Для Biographia — вторая строка с новым сгенерированным секретом, добавляется при подключении сервиса.

Это изменение независимо от остального Biographia-стека — можно сделать на стороне Dominex заранее, ещё до того как у Biographia появится код, которому есть смысл им пользоваться.

## 13. Единый экран настройки подключаемых модулей (Dominex «Настройки»)

Цель — один экран в Dominex, где заводится/донастраивается любой подключаемый модуль (Biographia и последующие) целиком: без ручного лазания по `.env`, миграциям и чужим админкам. Решено — вариант «толстый»: Dominex умеет не только показывать, что нужно сделать в `ssod_auth`, но и реально писать туда (например `sso_enabled`), а не просто давать ссылку.

**Новый канал.** До сих пор все межсервисные вызовы шли в одну сторону — `ssod_auth → Dominex` (`dominex_client.py` читает identity/projection). Толстый экран требует обратного направления: `Dominex → ssod_auth`, запись. Это новая привилегия, которой раньше не было, — обязательно свой отдельный секрет (не переиспользовать `SSO_TICKET_SECRET` и не переиспользовать секреты из 2.2, которые идут в обратную сторону), и обязательно узкий список полей, а не общий CRUD по модели — чтобы толщина канала не превращалась в произвольный RCE-по-смыслу доступ к чужой БД.

**Что входит в экран (по продукту, например `biographia`):**

1. **Основное (Dominex, локально)** — code/name/url/is_active каталога `Product` в самом Dominex. Уже существует в `/core/products/`, расширяется так, чтобы при сохранении **автоматически проталкивать** name/url/is_active в копию `Product` на стороне `ssod_auth` (через новый write-канал) — сейчас это две независимые копии, которые может незаметно рассинхронизировать, после изменения одно сохранение полностью описывает обе.
2. **SSO (запись в `ssod_auth`)** — переключатель `sso_enabled`, тем же write-каналом. Показывает и текущее значение, подтянутое оттуда же (если запись не удалась/сервис недоступен — явная ошибка, не тихий откат, тот же принцип, что в 10.2).
3. **Ключ Identity-API (Dominex, локально, из 2.2)** — список зарегистрированных консьюмеров (`ssod_auth`, `biographia`, …), кнопка «Выпустить ключ» показывает секрет один раз (как у `SSODAccessKey`), дальше только fingerprint + отзыв.
4. **Чек-лист для нового сервиса** — то, что физически придётся руками положить в `.env` **самого нового сервиса** при первом деплое (сгенерированный ключ из п.3, `SSOD_AUTH_PUBLIC_URL`, `SSO_TICKET_SECRET`) — экран не может дотянуться до чужого контейнера и записать файл сам, но собирает все нужные значения в одном месте для копирования, вместо их поиска по трём репозиториям. Честно показывается как последний ручной шаг, не автоматизируется полностью — див `.env` на каждом сервисе гитигнорится и не приезжает через `git pull` (уже известный урок из памяти интеграции).

**Новый API в `ssod_auth`** (принимает вызовы из п.1/2 выше): узкий `POST /api/v1/products/update/` по конкретным полям `Product` (`name`, `product_url`, `is_active`, `sso_enabled`), под своим отдельным секретом (`X-Dominex-Admin-Key`/`DOMINEX_ADMIN_API_KEY`), с записью в `AuthEvent` (новый тип `product_config_synced`) на стороне `ssod_auth` — чтобы изменение конфигурации продукта «через мост» было видно так же, как обычное ручное изменение через Django Admin, а не терялось как безымянный API-вызов.

**Реализовано и проверено сквозь реальный docker-стек 2026-07-13** (`dominex`, `ssod_auth`): `IdentityApiConsumer` (2.2), `Product.sso_enabled`-зеркало, write-мост и все три панели настроек — код есть, миграции накатаны, весь путь прогнан живыми контейнерами (create/update/idempotent-повтор/revoke, обратная совместимость старого ключа `ssod_auth`, отказ на неверный/отсутствующий ключ). Один пробел, который не был предусмотрен на этапе проектирования и всплыл только при реальном вызове:

**Docker service name с подчёркиванием не проходит валидацию Host-заголовка Django (RFC 1034/1035) — независимо от `ALLOWED_HOSTS`.** `ssod_auth_web` (реальное имя сервиса) физически не может появиться в `Host`-заголовке ни при каких настройках `ALLOWED_HOSTS` — Django отклоняет его на уровне regex ещё до сверки со списком. Раньше это было незаметно, потому что все входящие запросы к `ssod_auth` шли либо через nginx (публичный домен), либо с `localhost` в локальной разработке — этот write-мост стал первым вызовом по внутреннему docker-имени напрямую. Решение: `docker-compose.yml` сервиса `ssod_auth_web` получил дополнительный network alias без подчёркиваний — `ssod-auth-internal` — именно на него смотрит `SSOD_AUTH_INTERNAL_URL` в Dominex и именно он добавлен в `ALLOWED_HOSTS`. Стоит держать в уме при добавлении любых будущих server-to-server вызовов по docker-именам с подчёркиванием (в том числе когда появится сам сервис Biographia).

**Реестр ключей/устройств (раздел 4) — это `ssod_auth`, не Biographia.** Уточнение терминологии: «ЛК АУС» в разделе 4 означает именно `ssod_auth` (веб-чат, где готовился документ, не имел доступа ко всей системе и неточно назвал сервис). Практическое следствие: часть работы по ключевой модели — это **новые таблицы и API в `ssod_auth`** (список устройств, зашифрованные копии ключей, отзыв устройства), а не только код нового сервиса Biographia. Это осознанно принятая часть скоупа, а не побочный эффект — `ssod_auth` уже владеет WebAuthn/passkey-инфраструктурой, регистр ключей логически туда и относится, как часть единой экосистемы.

## 3. Зоны и модель безопасности

Каждая запись принадлежит одной из трёх зон. Зона определяет модель безопасности; ранг Dominex определяет вертикальный срез внутри незакрытых зон.

| | Открытая | Закрытая · юрлицо | Личная |
|---|---|---|---|
| Шифрование | нет | нет (изоляция) | да, ключ владельца (zero-knowledge) |
| Разделение | по рангам Dominex | строгая изоляция по юрлицу (`org_id` + RLS) | владелец |
| Поиск | полный, серверный | в рамках юрлица, серверный | только на клиенте |
| Доступ | по рангам | группа админов юрлица | только владелец |
| Назначение | вики, журналы, фото | документы/данные по юрлицу | дневник, личные заметки |

Решения:

- **Зона 2 (юрлицо) — изоляция, а не шифрование.** Цель — исключить пересечение информации между организациями, а не защита от кражи БД. Реализуется строгим `org_id`-скоупингом + Postgres Row-Level Security. Поиск и вики внутри юрлица сохраняются. Шифрование ключом юрлица можно добавить позже (ценой поиска по этой зоне), если появится требование по утечкам.
  - Уточнение по видимости внутри зоны: доступ — это членство в группе админов юрлица (таблица выше), а `access_level`/ранг (раздел 6.2) — дополнительный вертикальный срез **внутри** этого членства (админ юрлица с недостаточным рангом всё равно не видит запись). Обе проверки одновременно, не одна вместо другой — явно зафиксировать это в логике доступа, а не только в одной из двух формулировок документа.
  - RLS — это не только флаг в схеме: нужен реальный механизм простановки контекста организации на каждый запрос (`SET LOCAL` сессионной переменной Postgres в начале транзакции), иначе политики RLS не на что опереться. Также следствие: локальная разработка/тесты зоны 2 требуют настоящего Postgres с первого дня — SQLite-фолбэка (как у Dominex) для этой части не будет.
- **Зона 3 (личная) — единственная настоящая zero-knowledge.** Сервер хранит только шифртекст; расшифровка возможна только на устройстве владельца. Шаринга нет.
- Официальная лента объекта **рендерится под конкретного зрителя**: записи, на которые у зрителя нет прав (в т. ч. чужие личные), для него не отображаются вовсе.

> **Требование безопасности.** Перед доверием реального чувствительного контента личной зоне крипто-схему и её реализацию необходимо вынести на профессиональное ревью/аудит.

## 4. Модель ключей и устройств

Разделяем две вещи, которые нельзя смешивать:

- **Аутентификация** — passkey/SSO (одна личность, без паролей, со всех устройств и во всех разрешённых сервисах). Инфраструктура WebAuthn уже есть в `ssod_auth`.
- **Ключ шифрования** — секрет, которым открываются личные данные. Сервер не хранит его в пригодном для использования виде.

Принципы:

- У пользователя логически **один мастер-ключ** (шифрует его личные данные). В реестре (ЛК АУС) он хранится **не как ключ, а как отдельные зашифрованные копии под каждое устройство**. Каждое устройство открывает только свою копию; сервер — ни одну.
- **Добавление устройства:** вход в ЛК без пароля → уже подключённое устройство подтверждает новое и кладёт для него зашифрованную копию мастер-ключа → новое устройство разворачивает её локально. Модель Signal/Bitwarden/1Password.
- **Один ключ на все сервисы** — как ощущение; под капотом из корневого ключа выводятся по-сервисно подключи (HKDF с меткой сервиса). Подключ Biographia разворачивается автоматически при первом входе при наличии доступа — без действий пользователя.
- **Реестр (ЛК АУС)** — брокер и учётчик: список устройств и ключей, публичные данные, зашифрованные копии, отзыв потерянного устройства. Не хранилище рабочего секрета.

**Провайдер ключа — подключаемый (pluggable):**

- Есть FIDO2-токен → ключ устройства выводится из токена (WebAuthn PRF), не покидает железо; защита уже полученного ключа на устройстве от компрометации.
- Нет токена → платформенный passkey (Touch ID / Windows Hello).
- Нет ничего → пароль + seed-фраза.

ЭЦП/ГОСТ (юридически значимая подпись) в проекте **не используется** — избыточно и дорого под задачу.

**Восстановление:** пока есть хотя бы одно подключённое устройство — оно авторизует замену. На случай «потерял всё» — recovery-код / seed-фраза (BIP39), сохранённая оффлайн при первой настройке (единственное разовое действие от пользователя).

Ограничение доступа к токену из браузера: WebAuthn PRF в вебе поддержан неровно (Android — надёжно, Windows Hello — с обновления 02.2026, Safari/iOS — неполно), поэтому используется как усиление, а не критическая зависимость. В нативных клиентах (Tauri/RN) доступ к токену через PKCS#11 — прямой.

### 4.0. Первый срез (пароль+seed, без WebAuthn) — реализовано 2026-07-13

По решению пользователя первый проход строит только providers «пароль + seed-фраза», без WebAuthn PRF (раздел явно допускает это — «усиление, не критическая зависимость», можно добавить вторым шагом поверх уже рабочей схемы).

**Модель:** seed-фраза (BIP39, 12 слов) — источник истины мастер-ключа, не обёртка над отдельно сгенерированным случайным ключом (как в крипто-кошельках: мастер-ключ = `HKDF(mnemonicToSeed(фраза))`, детерминированно). Пароль не хранит ключ сам по себе — оборачивает (wraps) уже полученный из seed мастер-ключ через `Argon2id(пароль, соль) → XChaCha20-Poly1305`. Следствие: recovery по seed-фразе не требует **никакого** обращения к серверу для восстановления самого ключа — фраза сама по себе воспроизводит мастер-ключ локально; сервер нужен только чтобы затем сохранить новую обёртку под новый пароль.

**ssod_auth (реестр, раздел 4 — «брокер и учётчик, не хранилище рабочего секрета»):**
- Новая модель `PersonalKeyMaterial` (`accounts/models.py`): `wrapped_master_key`, `nonce`, `kdf_algorithm`/`kdf_salt`/`kdf_memory_kib`/`kdf_iterations`/`kdf_parallelism` — то есть только шифртекст и публичные параметры KDF, ничего похожего на секрет. **Упрощение этого прохода**: одна запись на пользователя (`OneToOneField`), не одна на устройство — настоящее distribution зашифрованных копий по нескольким устройствам («уже подключённое устройство подтверждает новое») не реализовано, схема полей уже готова под это (станет `FK` + `device_label`), сама крипто-схема не изменится.
- Новый API `POST /api/v1/personal-key/` и `GET /api/v1/personal-key/<username>/`, под своим отдельным секретом (`BIOGRAPHIA_KEY_API_KEY`) — тот же принцип «один секрет на канал», что и у admin-моста из раздела 13. Новое направление вызова: Biographia → ssod_auth, которого раньше не было для данных пользователя (только для конфигурации продуктов).

**Biographia:** `app/core/ssod_auth_client.py` (server-to-server клиент, отдельный от `dominex_client.py`), blueprint `app/crypto/` — `GET /crypto/status`, `POST /crypto/setup`, `GET /crypto/material`. Backend **никогда** не видит пароль, seed-фразу или расшифрованный ключ — только то, что уже зашифровано в браузере.

**Клиентский модуль** `frontend/src/crypto/masterKey.ts` — первый TypeScript-файл в проекте (раздел 5 предполагал TS с самого начала, реальный код до этой фазы был на JS; точечное добавление, не полный переход). Использует ровно то, что называл раздел 5: `@noble/ciphers`, `@noble/hashes` (включая `argon2`), `@scure/bip39`. Функции: `generateSeedPhrase`/`masterKeyFromSeedPhrase`/`wrapMasterKey`/`unwrapMasterKey`/`deriveSubkey`/`encryptText`/`decryptText`.

**UI** (`frontend/src/pages/DiaryPage.jsx`, заменил прежнюю заглушку): экран настройки (пароль → показ seed-фразы один раз → сохранение), экран разблокировки (пароль → расшифровка), форма восстановления по seed-фразе (новый пароль взамен забытого), и демонстрационная панель шифрования/расшифровки текста — доказательство, что подключ Biographia реально работает. Полноценная лента/календарь дневника (7.4) — отдельный следующий шаг, не в этом проходе.

**Проверено многослойно, не только «код компилируется»:**
1. Примитивы (`argon2id`, `xchacha20poly1305`, `hkdf`, BIP39) — проверены напрямую вне React.
2. Сам файл `masterKey.ts` (не переписанная копия логики, настоящий исходник через `tsx`) — детерминированность seed→ключ, явный отказ (throw) на неверный пароль вместо тихого провала, recovery-поток воспроизводит тот же мастер-ключ под новым паролем, юникод/эмодзи корректно проходят туда-обратно.
3. **Полный HTTP-путь реальными данными**: материал, посчитанный настоящим клиентским модулем → `POST /crypto/setup` → сохранён в `ssod_auth` → `GET /crypto/material` → побайтово совпадает с отправленным → расшифрован тем же модулем → совпадает с исходным мастер-ключом. Не через Vite dev-прокси (порт 5173) — контейнер `biographia_frontend` завис на уровне Docker-рантайма (`setns` отказал, `docker kill`/`stop`/`rm -f` не сработали) в процессе тестирования, тестировалось напрямую через порт backend (5000) плюс одноразовый `docker run` с чистым `node:20-alpine` для клиентской части — не баг кода, инфраструктурная случайность, требует перезапуска Docker Desktop для восстановления самого дев-сервера.

**Открыто:** WebAuthn PRF (FIDO2/passkey provider) — следующий шаг поверх уже рабочей схемы; настоящая multi-device дистрибуция зашифрованных копий; реальный клик-тест в браузере через порт 5173 (заблокирован зависшим контейнером, не кодом); полноценный UI дневника (7.4).

> **Требование безопасности не снято.** Это первый работающий срез, не аудит. Профессиональное крипто-ревью перед реальным чувствительным контентом (см. раздел 3) остаётся в силе.

### 4.0.1. WebAuthn PRF провайдер (второй шаг поверх 4.0) — реализовано 2026-07-14

Второй provider из раздела 4 («Есть FIDO2-токен → ключ устройства выводится из токена (WebAuthn PRF)») поверх уже рабочей пароль+seed-схемы — не замена, сосуществует: `PersonalKeyMaterial` теперь много записей на пользователя (по одной на provider/credential), а не одна.

**Ключевое разделение ответственности**, зафиксированное в докстринге `app/passkey/routes.py`: сама WebAuthn-церемония (проверяемая сервером подпись/аттестация) и PRF (секрет, который никогда не покидает браузер) — независимы. Python-библиотека `webauthn` (2.8.0) вообще не знает о PRF (`[n for n in dir(s) if 'prf' in n.lower()]` — пусто, проверено через `inspect.signature()`, не угадано); расширение `prf` добавляется вручную в JSON на фронтенде поверх того, что генерирует `generate_registration_options()`/`generate_authentication_options()`.

**ssod_auth (реестр):**
- Новая модель `WebAuthnCredential` (`credential_id`, `public_key`, `sign_count`, `transports`, `label`) — отдельно от `django_otp_webauthn`, который уже используется для входа: это **вторая, независимая регистрация** того же физического ключа, не переиспользование существующего логин-credential.
- `PersonalKeyMaterial.user` — было `OneToOneField`, стало `ForeignKey` (`related_name="personal_key_materials"`), плюс `provider` (`password` / `webauthn_prf`), `label`, nullable `webauthn_credential` FK, `kdf_*` поля стали nullable (у PRF-провайдера нет Argon2id — сам провайдер и есть KDF). Миграция проверена: существующая реальная запись пользователя сохранилась с `provider='password'`, ничего не потеряно.
- Новые эндпоинты под тем же `BIOGRAPHIA_KEY_API_KEY`: `POST/GET webauthn-credentials/`, `POST webauthn-credentials/<id>/sign-count/`. `store_personal_key_material`/`fetch_personal_key_material` переписаны на список (`{"materials": [...]}`) вместо одной записи.

**Biographia backend** — новый blueprint `app/passkey/` (не `webauthn/`, чтобы не затенять PyPI-пакет `webauthn`):
- `GET /webauthn/register/options`, `POST /webauthn/register/verify` — регистрация нового ключа; verify отклоняет (`authenticator_does_not_support_prf`), если браузер не подтвердил `clientExtensionResults.prf.enabled` — бессмысленно хранить credential, которым нельзя будет разблокировать.
- `GET /webauthn/authenticate/options`, `POST /webauthn/authenticate/verify` — разблокировка; `options` использует **фиксированную** соль (`b"biographia-personal-zone-v1"`) для `prf.eval.first` — случайная соль на каждой попытке сделала бы обёрнутый ключ невосстановимым после первой же разблокировки. `verify` обновляет `sign_count` best-effort (проглоченное исключение — пропущенное обновление счётчика не должно аннулировать уже состоявшуюся успешную разблокировку).
- `app/crypto/routes.py` переписан под список провайдеров: `GET /crypto/status` → `{"configured", "providers": [...]}`, `POST /crypto/setup` и `GET /crypto/material` принимают `provider`/`credential_id`.

**Фронтенд:**
- `masterKey.ts` — добавлены `wrapMasterKeyWithKey`/`unwrapMasterKeyWithKey`, общие AEAD-примитивы поверх уже готового ключа (не пароль-специфичные): и пароль-путь (`Argon2id → wrapMasterKeyWithKey`), и WebAuthn-путь используют один и тот же код шифрования, а не две независимые копии, которые могли бы разойтись.
- Новый `crypto/webauthn.ts` — `registerWebAuthnKey()`, `unlockWithWebAuthnKey()`, на `@simplewebauthn/browser` (13.3.0). **Важная деталь, не покрытая типами библиотеки**: PRF — расширение уровня 3, которого нет в бандлированном `dom.d.ts` (`AuthenticationExtensionsClientOutputs` не знает про `prf` вообще, хотя реальные браузеры его поддерживают) — обходится локальным типом-приведением. Библиотека также **не конвертирует** `extensions.prf.eval.first` из base64url-строки (как приходит с бэкенда) в `ArrayBuffer` — она передаёт `extensions` как есть (проверено чтением `startAuthentication.js`, не угадано), конвертация сделана вручную через экспортируемый `base64URLStringToBuffer`.
- `PersonalKeyContext.jsx` — теперь хранит и отдаёт список `providers`, `masterKey` (не только производный subkey) и `refreshStatus()`.
- `DiaryPage.jsx` — `UnlockForm` показывает кнопку «Войти через ключ «label»» для каждого зарегистрированного `webauthn_prf`-провайдера рядом с формой пароля; новая кнопка «Добавить ключ (WebAuthn)» доступна только после разблокировки (нужен `masterKey` в памяти, чтобы обернуть его под новый PRF-ключ) — раскрывает поле для метки ключа и запускает регистрацию.

**Проверено:**
1. Полный бэкенд-путь без реального токена (`test_webauthn_backend.py` через свежий SSO-тикет, замайненный напрямую через `jwt.encode` с секретом `ssod_auth`): `register/options` → 200, валидная форма (rp/user/challenge/`extensions.prf`); `authenticate/options` без зарегистрированных ключей → 404 `no_credentials_registered`; `register/verify` с мусорным credential → 400 `verification_failed` (не падает); `authenticate/verify` без ожидаемого challenge → 400 `no_pending_challenge`.
2. Реальный баг в процессе отладки, не в коде: `GET /webauthn/register/options` возвращал 404 несмотря на то, что `flask routes` показывал маршрут зарегистрированным. Причина — bind-mount (`.:/app`) плюс `gunicorn --workers 2` без `--reload`: воркеры были подняты до появления blueprint'а и не подхватили код без рестарта. `docker compose restart biographia_app` — маршрут заработал.
3. Установка `@simplewebauthn/browser` через именованный volume `biographia_frontend_node_modules` (не bind-mount) — та же защита от Windows-symlink проблем, что уже была у остального `frontend/`.

**Не проверено (требует реального железа/браузера, не может быть сделано мной):** живая церемония с реальным FIDO2-токеном/passkey — тап устройства, диалог браузера, PRF eval «в бою». Это следующий шаг для пользователя: открыть `http://localhost:5173/me` → «Личный дневник», разблокировать паролем, нажать «Добавить ключ (WebAuthn)».

### 4.0.2. Крипто-оракул (онлайн-ограничение подбора пароля через Dominex) — реализовано 2026-07-14

Закрывает пробел, обсуждённый отдельно от WebAuthn: расшифровка `wrapped_master_key` для пароль-провайдера была полностью локальной, значит тот, кто получил `wrapped_master_key`+`kdf_salt` (утечка БД, и т.п.), мог подбирать пароль офлайн неограниченно — единственной защитой была дороговизна Argon2id (64 МиБ/t=3), что также ощутимо нагружало мобильные устройства при каждой разблокировке.

**Решение** (полное обсуждение и обоснование выбора — в истории диалога с пользователем, не воспроизводится здесь): Dominex — единственный источник правды по идентичности в экосистеме — хранит секрет («перчинку») на пользователя, который **никогда не отдаётся ни по какому read-API**, только участвует в вычислении `HMAC-SHA256(секрет, intermediate)` по запросу, с проверкой статуса `User.is_active` и счётчиком попыток за окно. Это превращает офлайн-неограниченный подбор в онлайн-ограниченный: атакующий с украденным блоком не может продолжить подбор без обращения к Dominex, которое лимитировано.

**Осознанные компромиссы, подтверждённые пользователем явно:**
- Без запасного пути при недоступном Dominex — разблокировка временно не работает целиком, это принятый, а не случайный побочный эффект (раньше разблокировка была на 100% локальной).
- Простой HMAC-оракул, не полный слепой OPRF — теоретически чуть слабее (тот, кто одновременно наблюдает `intermediate` и ответ оракула на конкретную попытку — например, скомпрометированный бэкенд Biographia — может посчитать ключ для этой попытки напрямую), но кардинально проще в реализации; признано приемлемым.
- Никакой принудительной миграции для уже настроенного пароль-провайдера (реальный пользователь admin) — переход на новую схему естественный, при следующей смене пароля/recovery.

**Dominex** (единственное место, кроме Entity/Property системы, хранящее секрет — намеренно **вне** её: `AttachedProperty`/`FieldAccessOverride` ограничивают чтение по уровню допуска, но не исключают его полностью, а суперадмин с классом S всё равно смог бы прочитать property; секрету-«перчинке» это не подходит в принципе):
- Новые модели `app/models/crypto_oracle.py`: `CryptoOraclePepper` (секрет на пользователя, `LargeBinary(32)`, генерируется лениво при первом обращении), `OracleAttempt` (лог каждой попытки: `success`/`rate_limited`/`inactive`/`unknown_user`, с `client_ip` про запас для будущего fail2ban — не используется в самом лимите). Миграция `0021_crypto_oracle`.
- `app/api/oracle.py`: `POST /api/v1/oracle/evaluate` (под тем же `require_integration_key()`, что и остальные `/api/v1/identity/*` — Biographia уже имела свою строку в `IdentityApiConsumer`, новый секрет не понадобился) и `GET /api/v1/oracle/status/<username>` (read-only сводка для дашбордов). Лимит и окно — `ORACLE_RATE_LIMIT_MAX`/`ORACLE_RATE_LIMIT_WINDOW_MINUTES` (по умолчанию 20/60 мин), из env.
- «Рабочая область» (`/dashboard/`) — новая панель «Крипто-оракул» рядом с «Текущая сессия» (уменьшена и сдвинута вправо по образцу уже существующей двухколоночной сетки `.console-hero`, по просьбе пользователя со скриншотом), читает те же модели напрямую (без HTTP-прыжка, тот же процесс).

**ssod_auth:** `accounts/services/dominex_client.py::fetch_oracle_status()` — по тому же best-effort, никогда не бросающему стилю, что и `fetch_user_projection`/`verify_dominex_credentials`. Новая панель на `accounts/security.html` (та же страница, где уже показывается список WebAuthn-passkey для входа) — статус активности, попытки за окно, последний исход; при недоступности Dominex страница не падает, показывает «не удалось получить данные».

**Biographia backend:** `app/core/dominex_client.py::evaluate_oracle()` — в отличие от остальных вызовов в этом файле, возвращает структурированный результат (`rate_limited`/`inactive`/`unknown_user`/`oracle_unavailable`), а не просто `None`, потому что вызывающему нужно показать разное сообщение. Новый relay `POST /crypto/oracle` в `app/crypto/routes.py` — переправляет `intermediate` в Dominex и обратно, **нигде не логируя и не сохраняя** его самого.

**Фронтенд** (`masterKey.ts`):
- `DEFAULT_KDF_PARAMS` облегчён (64 МиБ/t=3 → 12 МиБ/t=2) — теперь запасной рубеж, а не основная защита; уже сохранённые записи не затронуты (unwrap всегда использует собственные `kdf_*` поля из конкретной записи, не эту константу).
- `deriveWrappingKey` переименован в `deriveIntermediate` (экспортирован) — на новом пути это не финальный ключ, а вход в оракул.
- `combineIntermediateWithOracleResult()` — `HKDF(ikm=oracleResult, salt=intermediate, "biographia-oracle-wrap-v1")`.
- `wrapMasterKeyWithOracle()`/`unwrapMasterKeyWithOracle()` — асинхронные, делегируют AEAD-часть в уже существующие `wrapMasterKeyWithKey`/`unwrapMasterKeyWithKey` (тот самый общий примитив, вынесенный ещё на шаге WebAuthn — окупился здесь без изменений).
- `kdf_algorithm` теперь `"argon2id" | "argon2id+oracle"` — `UnlockForm.unlock` ветвится по этому полю, старые записи разблокируются старым путём без оракула, новые (setup/recovery) — новым.
- WebAuthn/PRF-провайдер **не тронут** — оракул не нужен там, где нет подбираемого по словарю секрета.

**Проверено:**
1. Dominex напрямую: `evaluate` — детерминированный HMAC (одинаковый `intermediate` → одинаковый результат дважды), разный `intermediate` → разный результат, неизвестный пользователь → 404, лимит (20/60 мин) реально срабатывает на 21-й попытке подряд → 429.
2. Biographia relay через реальную SSO-сессию: проксирует `rate_limited` (429), корректно передаёт ошибки.
3. **Полный крипто-путь через реальный `masterKey.ts` (не переписанная копия, настоящий исходник через `tsx`)**: с mock-оракулом — round-trip восстанавливает мастер-ключ, неверный пароль корректно бросает исключение (invalid tag), ответ от «другого» оракула (имитация похищенного блока без доступа к реальной перчинке Dominex) тоже корректно проваливается — доказывает, что ответ оракула реально участвует в получении ключа, не декоративен. С **живым** оракулом (реальный HTTP через реальный relay Biographia → реальный Dominex, реальная сессия admin) — тот же round-trip, тот же корректный отказ на неверном пароле.
4. Обратная совместимость: старый `wrapMasterKey`/`unwrapMasterKey` (без оракула) по-прежнему работают независимо и корректно — проверено тем же прогоном.
5. Панель в АУС (`accounts/security.html`) и в Dominex (`/dashboard/`) отрендерены через тестовый Django/Flask-клиент с реальным логином admin — обе показывают корректные данные.

**Осознанно не проверено против реальной записи admin:** `POST /crypto/setup` с provider="password" для настоящего пользователя не вызывался в ходе тестирования — это перезаписало бы его настоящую (уже реально используемую) обёртку пароля. Слой хранения в ssod_auth (`PersonalKeyMaterial`) не различает содержимое `kdf_algorithm`, просто хранит строку как есть (прочитано в коде, не предположено) — новый путь не требует отдельной проверки этого слоя.

> Профессиональное крипто-ревью (раздел 3) по-прежнему не снято.

### 4.1. Привязка мобильного устройства (двухшаговый механизм, пользователю виден как одно действие)

Топология вызовов: мобильное приложение обращается **только к Biographia** (`biographia.ssod.pro`), никогда напрямую к `ssod_auth`. Biographia server-to-server проверяет ключ в `ssod_auth` — по тому же паттерну, каким `ssod_auth` уже сама дёргает Dominex через `accounts/services/dominex_client.py`. Это сознательный выбор: модуль сугубо биографии, а не общая точка входа для прочих продуктов.

**Шаг 1 — пейринг через одноразовый API-ключ.** В `ssod_auth` уже существует рабочий механизм `SSODAccessKey` (выпуск/отзыв в ЛК, `POST /verify-access-key`, секрет хранится только как SHA256-fingerprint). Для привязки устройства он используется так:

1. Пользователь в ЛК `ssod_auth` выпускает ключ, помеченный **одноразовым** (`single_use`), получает QR.
2. Мобильное приложение сканирует QR и отправляет ключ **в Biographia** (не в `ssod_auth`).
3. Biographia server-to-server вызывает `verify_access_key` в `ssod_auth`, получает identity (uuid, username, access_class, org, position).
4. В этом же вызове ключ **атомарно гасится** — повторно привязать им другое устройство или приложение нельзя.

**Доработка, необходимая в `ssod_auth`** (сейчас `verify_access_key` только обновляет `last_used_at`, ключ не гасит): добавить флаг `single_use` на `SSODAccessKey` и атомарное погашение ключа в том же запросе, где происходит проверка — не отдельным вторым вызовом, иначе возможна гонка (ключ успевает быть использован дважды до того, как погасится).

**Дальше Biographia выпускает собственный долгоживущий device-токен** (своя таблица, например `BiographiaDeviceSession`: `device_id`, привязанная identity, `issued_at`/`revoked_at`/`last_used_at`) — именно им телефон пользуется для всех последующих запросов. Побочный эффект такой схемы: скоупинг по продукту решается архитектурно, без доработки прав в `ssod_auth` — device-токен Biographia физически не предъявить никакому другому сервису экосистемы.

**Шаг 2 — мастер-ключ, полностью прозрачно для пользователя.** Сразу вслед за пейрингом, тем же потоком, устройство запрашивает у реестра `ssod_auth` свою зашифрованную копию мастер-ключа по уже описанной схеме "уже подключённое устройство подтверждает новое" (подтверждение может быть асинхронным). Пользователь не видит разделения на два шага — для него это один QR-скан, после которого телефон просто работает.

## 5. Технологический стек

**Бэкенд Biographia:** Flask 3.x (Flask-SQLAlchemy 2.x, Flask-Migrate/Alembic, psycopg2, PyJWT), gunicorn, Docker Compose, отдельная БД PostgreSQL. Хранит шифртекст/метаданные/привязки/учёт устройств.

**Деплой:** свой контейнер (свой внутренний порт в Docker-сети) на общем хосте, наружу — единый 443 через nginx+certbot на `biographia.ssod.pro`, тот же паттерн, что у Dominex/ssod_auth/ssod_site. Отдельный порт наружу не открывается — разделение по сервисам уже есть на уровне контейнера/поддомена; при будущем физическом разъезде по серверам (отказоустойчивость, территориальное распределение) внешний контракт (свой поддомен) не меняется, меняется только то, куда nginx проксирует.

**Клиентская крипта:** TypeScript, `@noble/ciphers` + `@noble/curves` + `@noble/hashes` (в т. ч. Argon2id) + `@scure/bip39`. Одна крипто-логика на все клиенты.

**Серверная крипта (если позже понадобится, напр. ключи юрлиц):** `PyNaCl` или PyCA `cryptography`.

**Клиенты (поэтапно):**

- Фаза 1 — веб-SPA: React + Vite на дизайн-токенах `atb-portal` (сайдбар, CSS-переменные, светлая/тёмная тема), как PWA (камера, установка, оффлайн) — покрывает «мобильный» сценарий без нативной разработки.
- Фаза 2 — десктоп: Tauri поверх той же сборки.
- Фаза 3 — мобильный натив: React Native/Expo, переиспользует общие TS-пакеты крипты и домена; QR-привязка устройств.

**Каркас реализован 2026-07-13** (`frontend/`): Vite + React + `react-router-dom`, CSS дословно перенесён из `atb-portal/backend/app/static/css/main.css`. JS, не TypeScript (в разделе выше про клиентскую крипту предполагался TS — на текущем этапе, без крипты, каркас на чистом JS; переход на TS понадобится к Фазе 1c, не переписывать всё заново, а добавить типы точечно). PWA (камера/офлайн/установка) не настроена — простой Vite-дев-сервер, без service worker.

**Хранилище медиа:** объектное (MinIO / S3-совместимое). Открытая зона — plaintext; личная — зашифровано на клиенте.

**Реализовано 2026-07-13**: MinIO поднят в `docker-compose.yml`, доступ через `boto3` (S3-совместимый клиент). Тот же класс проблемы, что и с Django/Vite в этой сессии — `boto3` тоже не принимает docker-имя с подчёркиванием как endpoint URL, решено тем же приёмом (алиас сети без подчёркиваний).

## 6. Модель данных

### 6.1. Сущности Dominex
Владелец сущностей — Dominex. Biographia ссылается на них по ID. Привязка возможна **только к сущностям**; к свойствам и шаблонам — нельзя. По умолчанию доступны только родительские сущности; составные под-сущности (сетевая карта, диск и т. п.) — за тумблером «показать составные элементы».

**Уточнение и реализация 2026-07-13.** На момент написания этого раздела ТЗ иерархии сущность↔сущность в Dominex физически не было — то, что здесь называлось «составными под-сущностями», в реальной модели было составным *свойством* (`PropertyTemplate` с `property_kind=COMPOUND`, например `logical_component`), не отдельной сущностью со своим ID. Это осознанное упреждение — механизм композиции (диск, пока лежит на складе, самостоятельная сущность; после установки в сервер становится дочерней, не переставая быть отдельно адресуемой; «рабочее место» может содержать системный блок + монитор, каждый из которых тоже отдельная сущность) обсуждался, но не был построен. Реализовано в Dominex тем же днём: `EntityInstance.parent_entity_id` (self-referential FK, миграция `0019_entity_parent`) — межшаблонная композиция (родитель и ребёнок могут быть разных `EntityTemplate`), с защитой от циклов и самоссылки в `/core/entities/<template_code>/<id>/` (выбор родителя, список «Составные элементы»). Теперь `parents_only` в поиске (раздел 8) имеет реальный смысл: `parent_entity_id IS NULL`.

Отдельно: у `EntityInstance` есть только `display_name`, нет `short_name` (в отличие от `Organization`, где оба поля есть) — «полное/краткое» название из раздела 7.1/8 буквально применимо только к юрлицам, для обычных сущностей есть только одно имя.

### 6.2. Запись биографии (официальная)
Атрибуты:

- `entity_id` — привязка к сущности Dominex (для непривязанных дневниковых записей — пусто).
- `zone` — open / org / personal.
- `org_id` — для зоны org.
- `access_level` — ранг Dominex (для open/org; у personal отсутствует).
- `type` — тип события: установка, документы, обслуживание, замена компонента, перемещение, инцидент, свободная заметка.
- `title`, `body` — заголовок и текст (оба опциональны при наличии вложений).
- `attachments[]` — вложения (см. раздел 9).
- `author` — из Dominex.
- `created_at`, версии — лента **append-only**: правка создаёт новую версию с историей, факт не переписывается молча.

**Реализовано и проверено сквозь реальный стек 2026-07-13** (`app/models/biography.py`, миграция `0002_biography_records`, `app/records/routes.py`):
- `entity_id` дополнен `entity_kind` (`entity`/`organization`) — привязка полиморфна, юрлицо тоже может быть субъектом записи (раздел 6.1), не только `EntityInstance`. Оба поля — обычные целочисленные колонки, не настоящий FK: Biographia не владеет таблицами Dominex (раздел 2), целостность не гарантируется на уровне БД.
- `type`/`title`/`body`/`access_level`/`zone`/`org_id` — как описано; `access_level` реально `nullable`, гарантированно `None` только для `personal`.
- Версии — отдельная таблица `BiographyRecordVersion` (`version_number` с 1), создаётся при каждом `POST /records/<id>/edit`; сама запись хранит только текущее состояние.
- **Floor-правило (10.1) проверено вживую**: создание с `access_level` ниже класса сущности → автоматически поднимается до класса сущности; класс сущности поднялся после создания записи → при следующем чтении записи (`GET /records/<id>` или в ленте) `access_level` подтягивается вверх сам (лениво, при обращении, не фоновой задачей); класс сущности понизился обратно → `access_level` записи остался на прежнем, более строгом уровне (асимметрия подтверждена, не понижается автоматически). Привязка отсутствует (`entity_id is None`) → floor не проверяется вовсе, как и было решено.
- **Fail-closed проверено**: если Dominex недоступен или сущность с указанным ID не существует **в момент создания** записи с привязкой — запись не создаётся (502), а не создаётся с непроверенным уровнем доступа. При чтении уже существующей записи Dominex недоступен — наоборот, best-effort (запись показывается с уже сохранённым уровнем, ресинхронизация просто не происходит в этот раз) — блокировать все чтения из-за временной недоступности Dominex сочли неверным compromise.
- **Видимость по зрителю (раздел 10) реализована и проверена юнит-тестом** (`can_view_record`): open — по рангу; org — членство в «группе админов юрлица» **и** ранг одновременно (интерпретация: `role=superadmin` видит любое юрлицо, `role=admin` — только своё, `role=user` — ничего в oргзоне; это прочтение таблицы раздела 3 через уже существующую в Dominex ролевую модель, отдельно с пользователем не переподтверждалось — пометка, а не тихое решение); personal — только автор.
- Пока не реализовано: вложения (раздел 9), комментарии (раздел 6.3), реальный UI (всё выше — JSON API, Phase 1 SPA ещё не начата).

**Дополнено 2026-07-13 (крипто-интеграция, раздел 4.0)**: для `zone=personal` добавлены `encrypted_content`/`nonce` (одно AEAD-сообщение на JSON `{title, body}`, не два раздельных шифртекста под одним nonce — см. docstring модели), `title`/`body` для personal-записей остаются `NULL` всегда. `create_record`/`record_edit` теперь взаимоисключающе требуют либо plaintext-поля (open/org), либо `encrypted_content`+`nonce` (personal) — попытка прислать plaintext для personal-записи отклоняется явной ошибкой, а не тихо игнорируется. Проверено прямым запросом к Postgres, что plaintext физически не попадает в БД.

### 6.3. Комментарии
Отдельный тип: неформальные заметки/пометки, не часть официальной истории, могут редактироваться/удаляться.

**Решено 2026-07-13, закрывает открытый вопрос раздела 12: комментарии — не сущность/фича Biographia вообще.** Это уже существующий механизм самого Dominex — «Комментарий» как всегда доступное attached-property на любой сущности (см. архитектурную память Dominex: «comment stays attachable everywhere via its own always-on carve-out»). Biographia ничего не строит под это — неформальные пометки живут и редактируются в консоли Dominex, как и раньше; официальные записи биографии (6.2) — отдельный, самостоятельный слой поверх тех же сущностей, не конкурирующий с этим механизмом и не поглощающий его.

### 6.4. Дневниковая запись (личная)
Универсальный блок: опциональный текст + опциональные вложения + опциональная подпись к каждому вложению. Может быть привязана к объекту (как личная запись по серверу) или свободной. Хранится в личной зоне (зашифровано, только владелец).

### 6.5. Единый источник — несколько представлений
Одна запись существует один раз, но показывается в: ленте объекта, разделах ЛК автора, личном дневнике. Везде — с учётом прав зрителя.

## 7. Экраны и интерфейс

Общий стиль — `atb-portal` (сайдбар, светлая/тёмная тема). SPA.

### 7.1. Централизованная вики (главная модуля)
- Вход — отдельная кнопка слева в консоли Dominex (при наличии права на Biographia).
- Лента последних правок/событий (≈10), по убыванию, **фильтруется под зрителя** (зона + ранг).
- Поиск по наименованию сущностей Dominex (полное/краткое), **не по содержимому**, с подсказками по мере ввода («Сер» → Сервер 1, Сервер 2, …). По умолчанию — только родительские; тумблер «показать составные элементы».
- Кнопка «Добавить запись»: текст + вложения + «прикрепить к сущности» (выбор из списка сущностей, тот же фильтр parents_only).

**Реализовано и проверено сквозь реальный браузерный путь 2026-07-13** (`frontend/` — Vite+React, дизайн-система перенесена дословно из `atb-portal/backend/app/static/css/main.css`): лента последних записей (`GET /records/recent` — новый эндпоинт, фильтрует по `can_view_record`, без пересчёта floor-правила на весь список ради скорости отклика), поиск сущностей с debounce (`GET /entities/lookup` — тонкий прокси к Dominex, браузер никогда не обращается к Dominex напрямую), форма «Добавить запись» (зона/тип/уровень доступа/привязка/текст). Тумблер «показать составные элементы» пока не выведен в UI — `parents_only` фиксирован в `true` на клиенте, сама фильтрация в Dominex уже работает (раздел 8).
- Проверено полным сквозным путём, каким пройдёт реальный браузер: тикет от `ssod_auth` → `/auth/sso/callback` через прокси Vite → редирект на `/` (SPA, не голый JSON) → сессия сохраняется → создание записей и лента отдают реальные данные.
- **Вход из сайдбара Dominex** — кнопки там пока нет (её появление относится к работе над самим Dominex UI, не Biographia); сейчас вход — прямой переход на `/auth/sso/authorize/biographia/` в `ssod_auth`.
- Dev-инфраструктура: `biographia_frontend` в docker-compose (`node:20-alpine`, `npm run dev`), проксирование API вместо CORS (`vite.config.js`) — браузер общается только с портом 5173, сессионные cookie выглядят same-origin. Ещё одна находка той же природы, что и раньше в этой сессии: Vite сам по себе тоже валидирует `Host`-заголовок (`allowedHosts`) — пришлось явно разрешить, иначе 403 при обращении не с `localhost`.

### 7.2. Страница объекта — лента биографии
- Хронология записей объекта с бейджами зоны и вложениями. Чужие/недоступные записи не показываются.

**Реализовано и проверено 2026-07-13** (`frontend/src/pages/EntityPage.jsx`, роут `/entity/:kind/:id`): карточка объекта (имя, шаблон, класс доступа), для сущностей — родитель и составные элементы (кликабельные, ведут на их собственные страницы — раздел 6.1's композиция), кнопка «Прикрепить запись» (форма с уже зафиксированной привязкой — первая половина двустороннего механизма из 7.5), лента записей объекта. Новый backend-прокси `GET /entities/<kind>/<id>` (карточка, отдельно от уже существующего `.../records` для ленты) — тот же принцип «браузер не говорит с Dominex напрямую», что и у поиска. Проверено на реальной паре родитель→ребёнок (`parent_entity_id`, раздел 6.1): карточка родителя показывает ребёнка, карточка ребёнка — родителя, запись, привязанная к дочерней сущности, получила её `access_level` через floor-правило (10.1).
- **Не сделано**: вторая половина 7.5 (прикрепление со стороны самого Dominex — «прикрепить запись биографии» на странице сущности в консоли Dominex) — это работа над Dominex UI, не Biographia, отдельная задача.

### 7.3. ЛК автора
- Карточка пользователя (ФИО, должность и т. д. — из Dominex).
- Три раздела записей под собственным авторством: общие; по организациям (с сортировкой); личные (с привязкой к объектам).
- Кнопка перехода в «Личный дневник».

**Реализовано и проверено 2026-07-13** (`frontend/src/pages/AuthorProfile.jsx`, роут `/me`): карточка (ФИО, должность, организация, роль, класс доступа), три секции из одного источника (`GET /records/mine` — все записи автора всех зон разом, группировка на клиенте, тот же принцип «один источник, несколько представлений» из 6.5), кнопка «Личный дневник».
- **Новый backend-эндпоинт `GET /profile`** (не `/me` — это имя уже занято роутом самого SPA; `/me` в проксируемых путях столкнулось бы с клиентским роутингом при прямом обновлении страницы) — перезапрашивает Dominex заново при каждом открытии страницы, не берёт из сессии: должности там никогда не было (не нужна была раньше), а класс/организация могли устареть с момента входа.
- **Группировка «по организациям»** сейчас подписана `Юрлицо #<id>` — имени юрлица нет в payload записи, только `org_id`; получение имени потребовало бы либо N обращений к Dominex на секцию, либо расширения `_record_payload`, что не делал в этом проходе — реальная, а не декоративная, а лишь недоделанная деталь.
- **Побочная находка**: сайдбар с самого начала подсвечивал «Вики» как активный пункт всегда, независимо от текущей страницы (было незаметно, пока существовал только один маршрут) — заодно переведён на `<Link>` вместо `<a>` (настоящая SPA-навигация без перезагрузки) и подсветка по текущему пути.
- **`/diary`** получил простую заглушку (не пустой 404) — реальный дневник осмысленно ждёт крипто личной зоны (Фаза 1c): хранить дневник в открытом виде до появления шифрования противоречило бы самой идее личной зоны, поэтому не стал имитировать интерфейс без реального содержимого за ним.

### 7.4. Личный дневник
- Два режима: **лента** (по дням, по убыванию; группировка по дню, сегменты по времени) и **календарь** (месяц; дни с записями подсвечены, пустые — нейтральны; иконки фото/файла/аудио; клик по дню → записи этого дня).
- Идея: насыщенность цвета дня по количеству записей (опционально).
- Добавление записей: свободный текст / фото с подписью / файл с пояснением / просто фото. На мобильном — быстрая кнопка «мгновенное фото».

**Реализовано и проверено 2026-07-14** (`frontend/src/components/DiaryFeed.jsx`, `DiaryCalendar.jsx`, `frontend/src/utils/dates.js`, переключатель режимов в `DiaryPage.jsx`):
- **Лента** — группировка по дню (убывание), внутри дня — по сегментам времени (Ночь/Утро/День/Вечер по часу создания). Заголовки дня — «Сегодня»/«Вчера» для последних двух дней, иначе `«8 июня 2026»` (родительный падеж, грамматически верно для этой формы).
- **Календарь** — сетка месяца (понедельник первым днём недели), навигация вперёд/назад, дни с записями подсвечены с насыщенностью по количеству записей относительно самого «плотного» дня месяца (опциональная деталь ТЗ — реализована), клик по дню показывает записи этого дня через тот же `RecordCard`, что и везде.
- **Не реализовано**: иконки фото/файла/аудио в календаре — личные вложения ещё не существуют (раздел 9), нечего было бы показывать; добавление записей с фото/файлом «на лету» — то же самое; кнопка «мгновенное фото» — мобильный сценарий, Фаза 3.
- **Найдена и исправлена грамматическая неточность в процессе разработки**: заголовок месяца в календаре сначала выходил в родительном падеже («Июня 2026»), пока не заметил и не завёл отдельный список названий в именительном падеже для этой формы (родительный корректен только в контексте «8 июня», не как самостоятельный заголовок).
- Проверено на реальных зашифрованных записях, раскиданных по нескольким дням и через границу месяца (искусственно сдвинутые `created_at` для теста) — группировка, сегменты, попадание в сетку календаря подтверждены настоящим модулем `dates.js`, не переписанной копией логики.

### 7.5. Прикрепление (двусторонний механизм)
Связь «запись ↔ сущность» создаётся как из вики (запись → прикрепить к сущности), так и со страницы сущности в Dominex (прикрепить запись биографии). Это одна связь, два входа.

## 8. Поиск

- Поиск по вики — только по наименованию сущностей (полное/краткое), не по содержимому.
- **Индекс наименований:** расширение Postgres `pg_trgm` + GIN-индекс по `display_name`/`name`/`short_name` (подстрока, устойчивость к опечаткам, ранжирование по похожести); либо btree `text_pattern_ops` для строгого префикса.
- Поиск по содержимому: открытая/оргзона — серверный; личная зона — только на клиенте (данные зашифрованы).

**Реализовано и проверено сквозь реальный стек 2026-07-13** (`dominex` `app/api/entities.py`, миграция `0020_pg_trgm_search`):
- `GET /api/v1/entities/search?q=…&parents_only=true[&limit=]` — ищет **и** по `EntityInstance.display_name`, **и** по `Organization.name`/`short_name` (это два разных объекта поиска, объединённые в один ответ), каждый результат помечен `"kind": "entity"|"organization"`. `parents_only` фильтрует по `parent_entity_id IS NULL` (раздел 6.1) — применимо только к `entity`, юрлица всегда верхнего уровня.
- `GET /api/v1/entities/<id>` — карточка сущности: включает `parent`/`children` (тот же вложенный формат, что и в результатах поиска).
- `GET /api/v1/organizations/<id>` — карточка юрлица отдельным эндпоинтом (не совпадает по форме с сущностью — `access_class`/`short_name`, без `parent`/`children`).
- Все три под тем же `X-Dominex-Api-Key`/`IdentityApiConsumer`-гейтом, что и identity-API (раздел 2.2) — проверено собственным ключом Biographia сквозь docker-сеть, не только с localhost.
- Строгий btree `text_pattern_ops`-префиксный поиск и ранжирование по похожести (`similarity()`) не реализованы — сейчас `ILIKE '%…%'`, ускоренный тем же GIN-индексом; типоустойчивое ранжирование можно добавить позже поверх того же индекса без новой миграции.

## 9. Медиа и вложения

- Типы: фото, сканы/файлы, аудио, видео.
- У каждого вложения — опциональная подпись/пояснение.
- Хранение: объектное хранилище; открытая зона — plaintext; личная — зашифровано на клиенте (пофайловый DEK).
- Превью/миниатюры (для личной зоны — тоже зашифрованы).
- Мобильный клиент: съёмка фото/аудио/видео «на лету» с моментальным прикреплением.
- Ведение личного архива вложений.

**Реализовано и проверено сквозь реальный стек 2026-07-13** (открытая/оргзона, plaintext — `app/models/biography.py::Attachment`, `app/core/storage.py`, миграция `0003_attachments`, MinIO в docker-compose):
- `POST /records/<id>/attachments` (multipart, поле `file` + опциональный `caption`), `GET /attachments/<id>` — отдаёт содержимое.
- Объект в MinIO адресуется случайным UUID, не оригинальным именем файла — оригинальное имя хранится только для отображения/скачивания, не участвует в пути.
- Право на загрузку — то же, что и на редактирование текста записи (`can_edit_record`, см. ниже): автор или суперадмин, не любой, кто может видеть запись. Право на скачивание — то же, что на просмотр записи (`can_view_record`) — вложение настолько же видимо, насколько сама запись, отдельного контроля доступа у него нет.
- Ограничение размера — 25 МБ, санитарный дефолт, не из ТЗ; пересмотреть, когда появятся реальные объёмы медиа.
- **Не реализовано**: личная зона (шифрование на клиенте, пофайловый DEK) — 501 на попытку загрузить вложение в `zone=personal`, явная ошибка, не тихий провал; превью/миниатюры; мобильная съёмка «на лету» (Phase 3); личный архив вложений как отдельный экран (UI ещё не начат).

**UI реализован и проверен 2026-07-14** (`frontend/src/components/AttachmentList.jsx`, встроен в `RecordCard`): до этого прохода backend был готов, но кнопки загрузки не существовало вообще — вложение нельзя было добавить через браузер. Список вложений — ссылки на скачивание (`<a href="/attachments/<id>">`, обычная навигация браузера, cookie идут сами, без fetch/blob); форма загрузки (файл + подпись) показывается только когда `canUpload` — новый `ViewerContext` (SPA-wide, App.jsx уже получал `/whoami` один раз, теперь раздаёт результат вниз по дереву без прокидывания пропсами) сверяет `record.author_username`/`role=superadmin`, то же правило, что и на backend (`can_edit_record`) — UI-подсказка, не единственная защита, сервер всё равно перепроверяет. Для `zone=personal` вместо формы — понятное сообщение «нужно шифрование по файлу», не скрытая или сломанная кнопка. Проверено сквозь реальный прокси-путь: создание записи → загрузка файла → скачивание → побайтовое совпадение содержимого.

**Побочная находка и исправление в этом же проходе**: редактирование записи (`POST /records/<id>/edit`) до этого было доступно любому, кто мог **видеть** запись (`can_view_record`), а не только автору — латентная дыра, не специфицированная в ТЗ явно, но противоречащая разделу 1 («официальная, **авторская**... запись»). Добавлена `can_edit_record` (автор либо `role=superadmin` как административное исключение, по аналогии с безусловным доступом SUPERADMIN в самом Dominex) — применена и к редактированию текста, и к загрузке вложений. Проверено юнит-тестом на реальном Flask test client с разными сессиями: суперадмин редактирует чужую запись, обычный не-автор — 403, при этом просмотр остаётся доступен.

## 10. Права, видимость, переходы

- Видимость определяется зоной + рангом Dominex; личное — только владельцу.
- Ленты (объекта и «последние правки») рендерятся под зрителя.
- **Переходы между зонами** возможны: открытая↔закрытая, открытая↔личная, между юрлицами. Механика: расшифровать (если источник зашифрован) → пересохранить по правилам целевой зоны → зачистить прежнее представление (plaintext, запись в индексе, старый шифртекст).
- Асимметрия: перевод **из личной** зоны возможен только на устройстве владельца (расшифровать может только он).
- Переходы логируются в Dominex (кто, что, когда), синхронизация поискового индекса при входе/выходе из открытой зоны.
- Категория выбирается при создании (Открытая / Юрлицо [какое] / Личная); дефолт — Открытая.

### 10.1. Уровень записи не может быть ниже уровня сущности (закрытие лазейки)

Все действия строго согласно уровню доступа. Найдена и закрыта конкретная лазейка: запись биографии создаётся с `access_level` не ниже текущего `access_class` привязанной сущности Dominex — но сущность может позже сменить свой уровень, и тогда уже существующие записи могут рассинхронизироваться с ней. Правило:

- **При создании** — `access_level` записи не может быть ниже `access_class` сущности на момент создания (ранг создателя и так это гарантирует по факту принадлежности, но проверка обязана быть явной, не полагаться на косвенное совпадение). Правило действует только когда у записи есть `entity_id` — непривязанные записи (дневник, свободные оргзаписи без объекта) им не ограничены, для них верхний предел — только ранг/область автора.
- **Если `access_class` сущности повышается** — все привязанные записи с более низким `access_level` автоматически подтягиваются вверх до нового уровня сущности. Информация не может остаться «более открытой», чем объект, к которому она относится.
- **Если `access_class` сущности понижается** — привязанные записи **не** понижаются автоматически, остаются как есть (могут быть строже, чем сама сущность — это безопасно). Ручное понижение уровня записи — отдельное явное действие администратора, не побочный эффект понижения уровня сущности.
- Асимметрия («поднимаем автоматически, опускаем только вручную») — сознательное решение: ошибочно заниженный уровень информации — риск утечки; ошибочно завышенный — просто неудобство.
- Это тот же принцип, что и floor/ceiling-модель access_class в самом Dominex (`stricter_access_class()`/`clamp_access_class()`), применённый здесь к связи «запись → сущность» вместо «свойство → владелец».

**Реализовано и проверено 2026-07-13** — см. раздел 6.2 (там же реализация "ручного понижения" как отдельного явного действия ещё не сделана: сейчас `access_level` можно только повышать через floor-механизм или задать при создании; прямое понижение задним числом не отличается от обычного редактирования — своего эндпоинта под это ещё нет).

### 10.2. Недостаточно прав — явное сообщение, не тихий отказ

Для любого эндпоинта чтения (карточка сущности, лента объекта, поиск и т. п.): если у пользователя нет прав на часть отображаемых элементов — не показываем их молча и не отдаём общий 403. Ответ явно сообщает, что часть данных скрыта из-за недостаточного уровня доступа («недостаточно прав для отображения всех элементов»), сами скрытые элементы в ответе отсутствуют. Разграничение «доступа к странице нет вообще» (реальный 403/redirect) и «страница доступна, но не весь её состав» (частичная лента + предупреждение) — это два разных случая, не путать.

## 11. Фазы реализации

1. **Фаза 1 — веб (MVP).** Flask-бэкенд Biographia + интеграция с Dominex/ssod; React-SPA/PWA; три зоны; модель ключей (пароль + passkey/PRF, seed-фраза); вики, объектная лента, ЛК, дневник с календарём; поиск по наименованиям; вложения.
2. **Фаза 2 — десктоп.** Tauri поверх веб-сборки; доступ к токену через PKCS#11.
3. **Фаза 3 — мобильный натив.** React Native/Expo; съёмка на лету; оффлайн-очередь; QR-привязка устройств.

**Ход работ внутри Фазы 1** (согласованный порядок — раздел 13's чат-обсуждение):

- **1a — Каркас и интеграция: готово.** Сервис Biographia (Flask, своя Postgres, Docker Compose, `biographia.ssod.pro` в плане), веб-вход через SSO-тикет (2.1), поиск/карточка сущностей и юрлиц (раздел 8), включая новую композицию сущностей в самом Dominex (`parent_entity_id`). Всё проверено сквозь реальный docker-стек, не только юнит-тестами.
- **1b — Открытая/юрлицо зоны без шифрования: backend готов, три экрана из четырёх (7.1–7.3).** Запись биографии с версионированием, floor-правило (10.1), видимость по зрителю, вложения (раздел 9, plaintext, MinIO) — всё как API, проверено. React-SPA: вики (7.1), страница объекта (7.2), ЛК автора (7.3, карточка + три секции записей). Не сделано: личный дневник (7.4 — сознательно заглушка, ждёт крипто из 1c), вторая половина двусторонней привязки со стороны самого Dominex UI (7.5), личная зона вложений, тумблер «показать составные элементы» в UI, имя юрлица вместо `#id` в группировке ЛК автора. Комментарии (6.3) закрыты как отдельный пункт — не входят в Biographia вообще, это существующий механизм самого Dominex.
- **1c — Личная зона + крипто: крипто-примитив и интеграция с записями готовы (пароль+seed, без WebAuthn).** Реестр в `ssod_auth` (`PersonalKeyMaterial`), прокси в Biographia (`app/crypto/`), клиентский TS-модуль (`masterKey.ts`), `PersonalKeyContext` на весь SPA — настройка, разблокировка, recovery по seed-фразе. **Личные записи теперь реально шифруются**: `BiographyRecord.encrypted_content`/`nonce` (раздел 6.2), `AddRecordForm` шифрует перед отправкой, `RecordCard` расшифровывает при чтении (или показывает «🔒 разблокируйте дневник», если ключ не разблокирован), `DiaryPage` — настоящая лента личных записей вместо демо-панели. Проверено сквозь весь HTTP-путь на реальных данных, включая прямую проверку в Postgres, что `title`/`body` для personal-зоны пусты, а plaintext не встречается нигде в ответах API. **Лента/календарь дневника (7.4) реализованы 2026-07-14** — группировка по дням/сегментам времени, месячная сетка с подсветкой по плотности записей, клик-по-дню. Не сделано: WebAuthn PRF, multi-device, личная зона вложений (`Attachment` всё ещё только plaintext, раздел 9 — из-за этого в календаре пока нет иконок фото/файла/аудио, нечего показывать), профессиональный крипто-аудит (обязателен перед реальным контентом). Следующее по согласованному порядку: WebAuthn, затем крипто-аудит.

## 12. Открытые вопросы и решения на потом

- Профессиональный аудит крипто-схемы личной зоны до загрузки реального чувствительного контента.
- Скоупинг `SSODAccessKey.permissions` по продукту в `ssod_auth` — отложено осознанно, не забыть. При выбранной схеме (одноразовый пейринг-ключ → собственный device-токен Biographia) общая проблема "ключ работает в любом сервисе экосистемы" снимается архитектурно; отдельный скоупинг в `ssod_auth` понадобится только если в будущем какой-то продукт станет использовать сырой `SSODAccessKey` напрямую, без обмена на свой токен.
- Новый статус/поле в `SSODAccessKey` для различения "погашен нормальным одноразовым использованием" (`consumed`) и "отозван вручную из осторожности" (`revoked`) — сейчас в модели есть только `REVOKED`, для одноразового пейринга стоит завести отдельное состояние, чтобы не терять этот нюанс в аудите.
- Шифрование зоны 2 (ключ юрлица) — отложено; включается при появлении требования по утечкам (с потерей поиска по зоне).
- Точная ранговая шкала (уровни доступа) — из существующей модели Dominex (буквенная шкала уже есть и используется, `access_rank()` в `app/core/access.py`); открытый момент — только как Biographia её получает: тянуть по API на каждое сравнение или зеркалировать константой с ручной синхронизацией при изменении в Dominex.
